## Building Blocks Are Different

A conventional function can satisfy its contract while the agent calling it misunderstands the task. The tool executes correctly, but the overall workflow still fails. That is a different problem from fixing an exception inside the function.

The architecture has to account for interpretation as well as execution. Give the model a clear job, expose the information it needs, and make the result inspectable before another action depends on it.

## Start with a Focused Job

One agent with a hundred tools can be difficult to debug. Splitting it into several agents adds handoffs and coordination, so that is a tradeoff to test rather than an automatic improvement. [Anthropic's agent-building guidance](https://www.anthropic.com/research/building-effective-agents) recommends starting with the simplest approach that works and adding complexity when it is needed.

* **Map the Work:** List the decisions and actions required, including where one result becomes another step's input.
* **Build One Useful Path:** Start with a focused agent or workflow and test it on representative tasks.
* **Separate Roles When It Helps:** Add a specialist when the work needs different context, tools, or an independent review. Keep responsibility for the combined result clear.

## Actively Manage the Agent's Memory

An agent's "context" is its working memory. The common mistake is to just keep adding information to it, thinking more data is always better. This leads to a cluttered and confused agent. Actively managing this memory is one of the most important jobs for a builder.

*   **Prevent Information Overload:** Don't just dump entire documents into the context. Use techniques to find the most relevant snippets first. Periodically, have the agent **summarize its work so far** to clean out old, unnecessary details.
*   **Stop Bad Information from Spreading:** A single wrong fact can "poison" the agent's memory, causing it to make a chain of bad decisions. By keeping the context clean and focused, you limit the damage of any single mistake.
*   **Let It Learn from Errors:** This is a crucial pattern. When an agent tries to run code and fails, don't just hide the error. **Feed the error message back into the agent's context.** The error can help the agent diagnose the failure and attempt a correction. Check the new result and bound retries so the loop does not keep repeating a bad approach.

## Test for Success, Not Just Accuracy

Testing an AI is tricky because it doesn't give a simple "pass" or "fail." It can be technically correct but completely wrong for your business, or it can sound confident while making things up. A new approach to testing is needed.

*   **List Your Failure Modes:** Create a checklist of all the specific ways the agent can fail. For a legal agent, this might include "missed a critical clause" or "misinterpreted a date." This gives you concrete things to test for.
*   **Use Real Experts to Grade It:** Software engineers are not qualified to judge an agent's medical or financial advice. Use **subject matter experts (SMEs)** to define quality criteria and review cases that require domain judgment. Combine that review with reference cases, executable checks, and evaluation of the completed workflow.
*   **Build a Test Suite from Real Data:** The best test cases come from your actual users. Log the agent's real-world interactions (especially the failures), and use this data to build a test suite that reflects how the agent will actually be used.

## Build a Safe Environment for Action

An agent that can take actions like executing code, sending emails, or deleting files is powerful but also dangerous. Safety cannot be an afterthought; it must be part of the initial design.

*   **Use a Sandbox:** Choose an execution environment with permissions appropriate to the task, and isolate untrusted code from resources it does not need. A **sandbox** isolates execution from the host environment. Its connected credentials, network access, and writable resources still determine what an action can affect.
*   **Set Up Guardrails:** Input and output checks can catch some suspicious instructions or sensitive content. Treat them as additional checks, with authorization enforced by the tools and services themselves. A classifier or a prompt cannot guarantee that an action is permitted.

## The Workflow Has to Handle a Wrong Answer

An agent can misunderstand the task even when each tool works correctly. The workflow needs enough structure to make that mistake visible: a source to inspect, a result to test, and a way to stop or recover before the next action compounds it.

That is the architectural work around the model. A reliable system has to account for what happens after a plausible answer turns out to be wrong.
