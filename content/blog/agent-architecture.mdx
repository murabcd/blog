## Building Operations Agents Can Use

A user asks an app to find notes from the meetings they had with the design team last month. The app already has a calendar and a notes library, but its interface may offer no way to connect the two. The data exists; the requested workflow was never built.

An agent-native application can expose calendar search and note search as tools. An agent can use those operations together, check the matches, and present the result. The developer still defines what the system can access and do. The agent chooses a sequence of supported operations for the user's request.

## The Rule of Equality

Treat the agent as a participant in the application. Important actions available through the interface should have corresponding operations the agent can use: create a folder, rename a file, search a document, or draft an email.

This parity has to include permissions and validation. A tool should enforce the same access rules as the human-facing path, and consequential actions may need confirmation. Giving an agent an operation that bypasses the application's rules creates a second, less trustworthy product.

## Give Tools Clear Boundaries

A tool such as `clean_up_inbox_and_archive_emails` hides several decisions inside one operation. That may be useful for a stable workflow, but it makes a poor general building block if users need different definitions of “clean up.”

Operations such as `read_email`, `archive_email`, and `create_folder` let the agent inspect messages and assemble a sequence appropriate to the request. The same tools might organize a client's correspondence or archive a specific category of messages.

Small operations also have costs. More calls can increase latency, and a long sequence can fail halfway through. Use higher-level operations where they preserve an important invariant or make a common task reliable. Tool boundaries should follow the product's behavior rather than a rule that every operation must be tiny.

## Combining Existing Capabilities

The calendar-and-notes example works only if the tools expose enough information to match records. The agent needs dates, participants, relevant text, and a way to handle ambiguous results. It may need to ask which design team the user means.

This is the useful part of the architecture: users can request combinations you did not build as dedicated screens. Watch those requests. Repeated combinations may deserve a saved workflow or a conventional interface that makes them faster and more predictable.

## Files as a Shared Workspace

Human-readable files can provide a convenient workspace for notes, drafts, and project context. Both the user and agent can inspect the same Markdown document, and changes can be reviewed with familiar tools.

Files are a design choice with limits. They do not remove the need for access control, concurrent-edit handling, search, or structured storage. Use them where their transparency helps; retain database constraints where the application depends on them.

## Give the Agent Current Instructions

An instruction file such as `AGENTS.md` can explain the workspace, the available tools, and the rules for making changes. Keep durable instructions separate from temporary task state so the file does not become a stale transcript.

Useful instructions cover:

- What the user is working on and where authoritative information lives
- Which operations the agent can perform and what requires approval
- How to verify a result and report uncertainty

The application must actually load the relevant instructions. A file in the repository has no effect if the runtime never reads it.

## Leave Room for an Unplanned Request

The calendar-and-notes request is the reason to build this way. The user needs a workflow that the application never received a dedicated screen for. Clear operations give the agent a way to assemble that workflow from capabilities the product already has.

Developers still own those capabilities, their rules, and the evidence that they worked. The architectural gain is that every useful combination no longer needs its own feature ticket before a user can try it.
