title: "Code Is Cheap. Decisions Are Expensive"
publishedAt: "2026-01-07"

## A Feature before the Decision

An agent can produce a prototype while the team is still debating whether the feature belongs in the product. That can be useful: a working example exposes constraints a discussion missed. It can also make a weak idea look more committed than it is.

The cost of producing an initial implementation has fallen for many tasks. Integration, testing, security, and maintenance still take work. The practical change is that a team can generate more candidate software than it has time to judge carefully.

## The Decision Queue

When implementation speeds up, unresolved choices become visible elsewhere. Product, design, and engineering still have to agree on the problem, the boundaries, and the reason to spend attention on it.

A team can accumulate work while it is:

- Debating which customer problem matters most
- Revising instructions that leave important behavior open
- Reconciling different assumptions about the intended result

Making more code does not resolve those disagreements. It may increase the cost of changing direction because there is now an implementation for someone to defend.

## Building the Wrong Thing Faster

Cheap experiments are useful when they answer a question. They become product clutter when every experiment is treated as a feature the company must carry indefinitely.

A technically successful change can still confuse the customer, overlap with an existing flow, or create a maintenance obligation larger than its value. Review the decision to keep it with the same care as the decision to build it.

## The Value of Precision

A useful specification names the intended behavior and the limits that matter. It leaves room for implementation judgment while making acceptance possible. For example, a faster approval flow still needs clear rules about who can approve and what happens when access changes.

The team needs to own both the reasoning and the checks. Agents can help write tests and explore alternatives, but those tests will reflect whatever assumptions the team gives them. Passing them cannot establish that the original problem was worth solving.

## Decisions Are the Work

When a team can produce candidate implementations faster than it can evaluate them, the slow part becomes choosing what deserves to exist. Someone still has to connect a customer problem to a specific behavior and decide whether the result is worth carrying.

That is where I think more of the value moves. Technical judgment still matters, including the judgment to reject generated code. The team also needs people who can make a useful choice before another afternoon of implementation gives everyone something to defend.
