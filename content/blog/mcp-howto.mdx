## Connecting an Assistant to a Tool

An assistant needs to create a calendar event. The integration has to expose the action, describe its arguments, handle authentication, execute the request, and return a result the assistant can use. Repeating that work for every host application creates another interface to maintain.

The Model Context Protocol provides a shared contract between an AI application and a server that exposes capabilities. The server can wrap an existing API. The protocol standardizes the exchange while the underlying service continues to do the work.

## The Host, Client, and Server

The [MCP architecture](https://modelcontextprotocol.io/docs/learn/architecture) separates three participants:

- **Host:** The AI application coordinating the interaction
- **Client:** The component the host uses to communicate with a server
- **Server:** The program exposing capabilities and context

A host may connect to several servers. One could expose file operations, another a business system, and another a search service. The host decides how available capabilities are presented to the model and how the resulting calls are handled.

## Describe a Tool's Contract

A server's tool definition includes a name, description, and input schema. The model can use that description to choose an operation and produce arguments. The server then validates and executes the call.

For illustration, an extraction tool might accept:

```json
{
  "name": "extract_product",
  "description": "Extract a product name and price from a page.",
  "inputSchema": {
    "type": "object",
    "properties": {
      "url": { "type": "string" }
    },
    "required": ["url"]
  }
}
```

This is a teaching example, not the current schema of a particular service. A provider such as [Firecrawl](https://github.com/mendableai/firecrawl-mcp-server) defines its own operations and supported arguments. Read the server's actual definitions before constructing a call.

## Discovery Helps Keep Integrations Aligned

The client can discover the [tools a server exposes](https://modelcontextprotocol.io/specification/2025-06-18/server/tools), including their schemas. This reduces dependence on manually copying documentation into a prompt and supports reuse across compatible hosts.

Discovery cannot establish that the description is accurate or the operation is safe. The host needs to decide which servers it trusts, which tools are available for a task, and how to respond when the advertised capability changes.

## Execution Still Needs Validation

Moving request construction into server code reduces the amount of integration logic the model must generate. The model can still choose the wrong tool, supply a valid but inappropriate argument, or misunderstand the result.

Validate inputs and enforce authorization on the server side. For consequential actions, the host may also need a user decision before execution. Permission prompts are part of the application's control design; their presence alone does not prove that every operation has the right boundary.

Inspect failures in the full sequence: tool choice, arguments, server execution, and result interpretation. A well-formed protocol message can still produce the wrong business outcome.

## Local and Remote Connections

MCP supports different [transport mechanisms](https://modelcontextprotocol.io/specification/2025-06-18/basic/transports). A local server can use standard input and output streams as a child process. A remote server can communicate over HTTP using the supported transport.

Choose the deployment based on where the data and permissions belong. A local server may be useful for files on a workstation, while a shared service may fit a business integration. Both require attention to credentials, access scope, and what information crosses the boundary.

## Start with an Inspectable Integration

Official SDKs for [TypeScript](https://github.com/modelcontextprotocol/typescript-sdk) and [Python](https://github.com/modelcontextprotocol/python-sdk) provide implementation support. The [MCP Inspector](https://github.com/modelcontextprotocol/inspector) helps examine an integration's exposed capabilities and behavior.

Begin with one useful operation and test its success, invalid inputs, denied access, and upstream failure. Add related tools once the host can explain what ran and what happened. This creates a more useful foundation than connecting a large tool catalog before anyone knows how failures will appear.

## Test the Operation Behind the Protocol

For the calendar example, verify the event's time, timezone, participants, and destination calendar after the call. The protocol made the integration reusable; the product still has to establish that the requested event was created correctly.

That division of responsibility is worth keeping clear. MCP supplies a common interface, and the application remains accountable for how that interface is used.
