## The Same Correction Again

An assistant makes a mistake, receives a correction, and handles the immediate task better. In a later session it makes the same mistake because the correction was never stored or retrieved. The conversation improved the current response without changing the system's future behavior.

For deployed agents, that distinction matters. A model's weights may remain fixed while the surrounding application changes its instructions, retrieved knowledge, and remembered task state. Those text-based changes can support useful adaptation when the system manages them deliberately.

## Weight Updates Have a Different Cost

Fine-tuning can change a model's behavior across many examples. It also requires suitable data, evaluation, and a deployment process. Updating a shared model with private user information creates additional isolation and governance questions.

For a task-specific correction, changing stored context can be a more direct first step. The team can inspect the rule, limit it to the relevant workspace, and remove it when it becomes stale. This complements model training rather than establishing that weight updates have no place in agent systems.

## What Token-Space Learning Means

Here, learning in token space means changing the text the system supplies to a model on later tasks. That might be a user preference, a verified workflow constraint, or a lesson from a failed operation.

The representation has practical benefits:

- **Inspection:** People can read the stored rule and its source.
- **Versioning:** Changes can be compared and rolled back.
- **Portability:** Stored knowledge can be tested with another model.

Portability does not guarantee identical behavior. A new model may interpret the same instruction differently, and a human-readable memory can still contain a wrong generalization. Evaluate the resulting behavior after a change.

## A Transcript Is Not a Memory Policy

Appending every interaction preserves history but leaves the next task to find the useful parts. Conflicting instructions and old assumptions can remain beside current decisions without a clear priority.

A memory policy should distinguish task state, durable preferences, verified facts, and tentative observations. Keep the source and scope of a lesson so an event from one project does not silently become a rule for every user.

Retrieval also matters. A useful correction that never reaches the relevant task has no practical effect, while an irrelevant correction can make the task worse.

## Consolidate with Review

A background process can examine recent interactions, identify repeated corrections, and propose a shorter representation. It should preserve provenance and avoid converting an uncertain interpretation into an established fact.

Give memory edits the same scrutiny as other behavior changes. Check for private information, conflicting instructions, and rules whose scope is wider than the evidence. Keep previous versions so an incorrect edit can be reversed.

## Let the Agent Propose a Lesson

An agent can identify a recurring failure and propose a correction for future runs. The application should decide which memory locations it may edit and which instructions remain protected. Task data must not gain authority merely because it appears in a document the agent read.

For example, a correction about a repository's test command can belong in that workspace's instructions. A note from an untrusted page telling the agent to ignore its rules should not. The storage and retrieval design needs to retain that distinction.

## Learn Fast, Distill Slowly

Text memory gives an agent a place to retain a correction without waiting for a training run. The lesson can be inspected, changed, or removed, and it can survive replacing the model underneath it. That continuity is part of the product the team is building.

Some stable patterns may later justify fine-tuning or other training changes. First the system needs to show that it remembers the right lesson and applies it in the right situation. Stored context becomes learning when it changes the next relevant piece of work.
