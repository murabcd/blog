## The Weight of Possibility

In traditional software, we avoid loading every library before the application needs it. With agents, we can make the same mistake in a different place: filling the context with every available tool definition before knowing what the task requires.

MCP makes tools easier to connect. It does not require the host to present the entire catalog to the model on every turn. That choice belongs to the application, and it can become expensive as the catalog grows.

## The Cost of Being Prepared

A tool definition takes space even when the agent never calls it. Descriptions, argument schemas, and examples can consume a substantial part of the input before the user's task begins. The cost depends on the actual definitions, model pricing, and caching; there is no useful universal cost per connected tool.

Measure the catalog in your own runtime. Compare how much context it occupies with how many tools a representative task actually uses. A large gap gives you a concrete reason to change how discovery works.

## The Skill Pattern

[Agent Skills](https://www.anthropic.com/research/equipping-agents-for-the-real-world-with-agent-skills) package instructions, scripts, and supporting resources. A short name and description can be available first, with the full instructions loaded when the task needs them. A skill can explain how to use tools, but it is not itself a tool server or an automatic permission boundary.

The same progressive-disclosure idea can apply to tool definitions:

1. **Describe What Is Available:** Give the agent a compact way to find a capability.
2. **Load the Relevant Contract:** Retrieve the actual tool schema or API definition when the task needs it.
3. **Execute through the Host:** Validate arguments and enforce access in the system that runs the operation.

Anthropic's [code execution with MCP](https://www.anthropic.com/research/code-execution-with-mcp) describes one implementation: expose tools as code APIs and let the agent inspect relevant definitions. Skills and deferred tool discovery are related ways to manage context, with different responsibilities.

## Curating the Toolkit

A documentation task may need navigation and page reading without performance tracing or device emulation. Start with that scope and leave a discovery path for a genuinely missing capability. Hiding too much can make the task fail just as loading too much can make it harder to navigate.

Filtering what the model sees also differs from restricting what it can execute. The host must enforce permissions even if a tool is absent from the current menu. A shorter prompt cannot replace that control.

## Agents Should Travel Light

A capable agent needs a way to discover what it can do, then enough detail to use the relevant capability correctly. Making every definition available in advance asks each task to carry the cost of every other possible task.

Keep the catalog discoverable and the working context focused. The test is whether the agent completes the work with less overhead while still finding the tools it actually needs.
