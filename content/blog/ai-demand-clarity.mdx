## Fast Code Exposes Unclear Decisions

Ask an agent to simplify onboarding and it can produce a working change before the team has agreed on what makes onboarding difficult. It might remove a step that supports an important customer requirement, or redesign a flow whose real problem is missing data.

The implementation can look finished while the decision remains unresolved. The team then spends its time reviewing assumptions that should have been discussed before the change was built. Faster coding makes this cost visible earlier and more often.

## Ambiguity Becomes an Implementation Choice

Human teams fill gaps through conversations, shared history, and questions during implementation. Agents can ask questions too, but they need enough context to recognize which uncertainty matters. Otherwise they choose a plausible interpretation and continue.

A useful brief explains the behavior you want to change, the evidence behind it, and the constraints that must remain intact. “Improve onboarding” leaves most of that open. “Reduce the work required for an invited teammate to reach their first shared project, while preserving admin approval” gives the implementation a boundary.

The brief should also identify decisions the agent must bring back to the team. Precision includes knowing where the specification ends.

## Keep the Working Context Consistent

An agent working from an old branch can implement the right idea against the wrong version of the product. A strategy document, design example, and API contract may each describe a different state. Humans encounter this problem too, but rapid automated changes can multiply the resulting rework.

Tell the agent which checkout and reference implementation are authoritative for the task. Keep changes small enough to reconcile, and update the specification when the team changes its mind. Branching models should fit the team's release needs; the immediate requirement is a clear view of the state being changed.

## Put Intent Beside the Implementation

Versioning requirements with the code gives reviewers a way to compare the intended behavior with the actual change. The repository can hold examples, business rules, design components, and acceptance checks that both people and agents use.

Each discipline contributes a different part:

- **Product:** The user problem, desired behavior, and evidence of value
- **Design:** Interaction rules, component examples, and important states
- **Engineering:** Architecture constraints, interfaces, failure handling, and verification

Some questions will remain open. Record those explicitly instead of hiding them in prose that sounds complete. A shared source of intent is useful because it makes disagreement visible and keeps the decision history close to the implementation.

## Define What Correct Means

Product leaders need to help define acceptance criteria that describe business behavior. For an approval flow, that includes who may approve, what happens when approval is revoked, and what the person sees while waiting. A screenshot alone cannot answer those questions.

Tests can encode parts of this intent, but the team still needs to judge whether the behavior solves the original problem. A passing test proves the conditions it checks. It can faithfully preserve a bad assumption if nobody challenges the premise.

## Clarity Becomes the Bottleneck

AI makes implementation cheaper and vague thinking more expensive. A decision the team has avoided can become working software before anyone notices that the agent had to make it for them. The review then becomes an argument about intent disguised as an argument about code.

That is why I think product teams need to spend more effort defining what should happen and what would count as correct. The time saved on implementation is valuable only if the team can turn it into a better choice about what to build.
