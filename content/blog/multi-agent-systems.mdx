summary: "Multi-agent systems are starting to work, but not as chaotic swarms. The useful pattern is much narrower: keep decisions centralized, let other agents add intelligence, and treat context handoff as the real architecture."
---

## Independent Work Creates Shared Decisions

A coding task is split across several agents. One chooses a permission rule, another invents an error state, and a third introduces a new abstraction. Each change can look reasonable in isolation while the combined product behaves inconsistently.

Parallel work includes decisions about interfaces, behavior, and architecture. A system needs a way to reconcile those decisions before treating the separate outputs as a completed task. Otherwise the integration cost can consume the time the extra workers saved.

## Give the Work an Owner

A useful starting point is one agent responsible for the main goal, plan, tradeoffs, and final result. Other agents can investigate a question, review an artifact, or implement a bounded piece of work. Their findings return to the owner so the plan can change coherently.

The write path needs clear boundaries. Independent files or components can sometimes be changed in parallel, while shared interfaces need agreement. Decide who integrates the work and who checks that the combined behavior still matches the request.

## Give Each Role Relevant Context

Copying the full conversation into every worker carries old assumptions and abandoned approaches alongside current decisions. A reviewer can benefit from seeing the goal and actual artifact without inheriting every explanation that made the builder comfortable with it.

Supply the relevant constraints, evidence, and question. Add history when it explains a tradeoff the reviewer needs to assess. Too little context produces generic advice; too much can reproduce the confusion the second perspective was meant to resolve.

## Review Findings before Applying Them

A build-and-review loop separates generation from a fresh examination of the result. A reviewer can inspect logic, missing cases, security boundaries, and whether the implementation matches the intended behavior.

Review comments remain claims to investigate. The owner should reproduce a reported bug, compare a suggested change with the task, and reject work that expands the scope without a reason. Blindly applying every comment can make the product less coherent even when the reviewer finds real issues.

## Escalate a Specific Uncertainty

A faster or less expensive model may handle routine work and request another perspective when a decision becomes difficult. Architecture questions, confusing failures, and security-sensitive changes can benefit from that escalation.

The challenge is recognizing when to ask and framing a useful question. Send the uncertainty, relevant evidence, attempted explanations, and the decision that needs help. A stronger model given the wrong problem can still return a confident answer to it.

Measure whether escalation improves completed tasks enough to justify its cost and latency. The existence of another model is only useful when the handoff lets it contribute something the current process is missing.

## Make Discoveries Change the Plan

A worker may discover that the assigned task rests on a false assumption. The system needs a path for that discovery to reach the owner before the rest of the work continues. Reporting only the final output can make the finding arrive too late.

Keep task state and dependencies visible. Identify which findings require a pause, which can be incorporated locally, and which need a user decision. This is especially important when workers share resources or can create external side effects.

## Coordination over Swarms

I would start with one agent that owns the result and add other roles where the work benefits from another perspective. Research, review, debugging, and escalation can all help. Each role also creates a handoff someone has to integrate.

The manager is responsible for keeping those contributions coherent: deciding which findings matter, which assumptions changed, and what the combined result should be. More workers make that responsibility more important. A system can produce a lot of individually reasonable work and still fail at the task that brought the agents together.
