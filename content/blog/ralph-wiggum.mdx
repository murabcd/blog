## The Problem with Chatting

Most developers use AI agents like a chat buddy. You open a window, paste in a request ("Make the button blue"), wait for the code, paste it into your editor, fix the inevitable bugs, and repeat.

It is faster than coding by hand, but you are still the bottleneck. You have to be there. You are the human router passing data back and forth.

A new pattern called "Ralph" flips this model. Instead of a conversation, it’s a **loop**. You give the AI a plan, a set of tools, and a simple script. The AI wakes up, grabs the first task, finishes it, commits the code, and then *restarts itself* to do the next one. The loop can make progress without a person handing over every next task. Whether that progress is useful still depends on the task definition, checks, and later review.

## How Ralph Works

[Ralph](https://ghuntley.com/ralph/) describes a repeated coding-agent loop. The example here combines that idea with a task list and progress notes; it is one possible implementation, rather than a required file format or an official product setup.

This version starts a fresh agent invocation for each iteration. The next run reconstructs its task from the repository, plan, and notes instead of inheriting the whole conversation. That can leave irrelevant history behind, but it also makes the quality of the handoff important. Restarting does not undo earlier changes or guarantee a better decision.

To make this work, you need three things:
1.  **The Brain:** A CLI agent (like Anthropic's `claude`).
2.  **The Plan:** A file (like `PRD.md`) that lists what needs to be done.
3.  **The Memory:** A file (like `progress.txt`) where the agent writes notes to its future self.

## The Blueprint: How to Build It

The following sketch shows how the pieces fit together. It omits runtime permissions, spending controls, recovery, and a reliable external completion check. Configure those for your agent and environment before treating the loop as unattended automation.

### 1. The File Structure
Create a folder in your project (e.g., `ralph/`) and add these files:

```text
/ralph
  ├── PRD.md          # The list of tasks (Product Requirements Document)
  ├── progress.txt    # The shared memory log
  └── loop.sh         # The script that runs everything
```

### 2. The Plan (`PRD.md`)
This is your backlog. The trick is to be extremely granular. Don't write "Build Login." Break it down so each step fits in one context window.

```markdown
# Product Requirements

- [ ] Create the database schema for the User table
- [ ] Create the server action for user registration
- [ ] Build the registration UI form component
- [ ] Add Zod validation to the form
- [ ] Write a test for the registration flow
```

### 3. The Loop Script (`loop.sh`)
This is the engine. It runs the agent, captures the output, and checks if the job is done.

```bash
#!/bin/bash
set -e # Stop if any command fails

# Run for 10 iterations (or however many you need)
for ((i=1; i<=10; i++)); do
  echo "🚀 Starting Iteration $i…"

  # Run the agent (using Claude Code)
  # We pipe the prompt directly into the agent
  result=$(claude -p "
    You are an autonomous developer.
    1. Read 'ralph/PRD.md' to see what needs to be done.
    2. Read 'ralph/progress.txt' to learn from past mistakes.
    3. Pick the first unchecked task.
    4. Implement it. Run tests to verify.
    5. Commit your changes: 'feat: [task name]'
    6. Check the box in PRD.md.
    7. Append lessons learned to progress.txt.
    
    If all tasks are checked, output: <STOP_SIGNAL>
  ")

  # Print the result to the console so you can see it
  echo "$result"

  # Check if the agent is finished
  if [[ "$result" == *"<STOP_SIGNAL>"* ]]; then
    echo "✅ All tasks complete!"
    exit 0
  fi

  echo "Sleeping for 5 seconds…"
  sleep 5
done
```

## Carry Lessons between Runs

The `progress.txt` file gives the next invocation a place to find decisions and corrections that would otherwise disappear with the conversation. A useful entry records what failed, what fixed it, and the conditions under which the fix applies.

For example, after a failed test command, the agent can record the actual command the project requires and the evidence that it passed. The next run can use that note and check whether it remains current. Copying an unverified guess into the file would preserve the mistake instead.

These notes change the context supplied to later runs. They do not update the model's weights, and their value depends on whether the later run finds and applies the right lesson.

## Success Factors

The loop needs a bounded task and feedback strong enough to stop a bad attempt from becoming the next run’s starting assumption.

* **Bounded Tasks:** Choose a change small enough to complete and verify within one run. An arbitrary time limit does not establish the right scope; the task needs a clear completion condition.
*   **Fast Feedback:** The agent needs to know if it succeeded. Your project needs a reliable command (like `npm test` or `npm run typecheck`) that the agent can run to verify its own work before committing.
* **Scoped Execution:** Use a disposable workspace and permissions limited to the task. A container can help isolate execution, but mounted files, credentials, and network access still determine what it can affect. Keep iteration and spending limits outside the model, and verify completion outside its own stop signal.

## Own the Loop

A coding loop moves some of the repeated coordination into software. The plan supplies the next task, the checks return feedback, and the repository carries the result into another iteration. A commit records what happened; it does not prove that the feature is finished.

The engineer still owns the conditions under which the loop runs and the review that follows. If each iteration leaves a result the next one can trust, unattended work can be useful. If the checks are weak, the same loop can compound a mistake while producing a very convincing history of progress.
