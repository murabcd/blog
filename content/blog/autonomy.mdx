## The Laptop Test

Start a task, close the laptop, and come back later. If the run stopped because a terminal closed or a local connection disappeared, the agent depended on the user's session even though the interface called it autonomous.

For work that must continue unattended, the execution loop needs an independent host and durable task state. The user should be able to reconnect, inspect progress, and interrupt the run without having to keep the process alive themselves.

This is a systems problem alongside a model-quality problem. A capable model cannot recover work that the runtime never recorded.

## The Threat of Environment Garbage

Agent runs create files, install packages, change configuration, and start processes. Reusing an environment can make a later run depend on an earlier run's leftovers. A cached package may hide a missing dependency; a lingering process may occupy a port.

Isolation helps expose those dependencies. For suitable tasks, start an ephemeral sandbox from a defined image, seed the required data, and retain the logs and artifacts needed to inspect the result. Destroying the workspace should not destroy the only evidence of what happened.

Some tasks require persistent state or access to an existing service. Keep that state explicit and separate from disposable execution. A sandbox reduces interference, but the permissions and connected systems still determine the consequences of a mistake.

## Severing the Connection

Decouple the user interface from the worker. The client submits a task, receives progress, and can disconnect while a coordinator retains the run's state.

Bound the worker's authority with explicit constraints:

- **Time:** Stop a run after its allowed execution window.
- **Cost:** Stop or request a decision when the spending limit is reached.
- **Access:** Restrict credentials, network destinations, and writable resources.

Approval can remain appropriate for consequential actions. Decide those boundaries before execution where possible, and preserve a waiting state when the agent needs a decision. Unattended operation should fit the task's authorization rather than remove it.

## Use the Interface That Fits the Work

For repository work, a shell can be an effective interface. Existing commands expose files, processes, HTTP requests, and exit codes in a form the agent can inspect. A small wrapper around `curl` may add little when the environment already supplies the required capability.

Purpose-built tools can still enforce permissions, validate arguments, or provide structured results that a raw command cannot. Protocols such as MCP can connect an agent to operations outside its sandbox. Choose the interface by its reliability and boundaries, then measure it on real tasks.

The operating system supplies useful primitives, but process isolation and network restrictions require actual configuration. Giving the model a shell does not establish those controls by itself.

## Define Outcomes and Constraints

A task needs a clear definition of completion. “Fix the typo” and “make the linter pass” describe different outcomes, even if they happen to touch the same file. Preserve the user's intent when converting a request into checks.

For exploratory tasks, let the agent choose and revise a plan within defined limits. For a migration or deployment, a fixed sequence may protect important invariants. The right amount of procedural detail depends on what can fail and how reversible the work is.

Record intermediate state so a retry can distinguish completed steps from work that needs repeating. External side effects need particular care: retrying an interrupted request must not accidentally duplicate a purchase or message.

## Benchmarks and Bills

An unattended loop can make calls much faster than a person reading and responding. Retries, exploration, and tool output can accumulate cost before anyone returns to the interface.

Track spend per completed task alongside success rate, latency, and recovery behavior. Evaluate representative failures, including a lost connection or a tool timeout. A cheaper run that leaves the task incomplete may cost more once someone has to reconstruct it.

## The Runtime Has to Carry the Task

The laptop test makes the infrastructure problem hard to avoid. An agent that needs the user to keep a terminal alive still depends on that person to carry the task through the day.

Independent execution, durable state, isolation, and bounded recovery give the agent somewhere to work after the user leaves. A better prompt can help it use that environment. The runtime has to keep the work alive.
