## What Is Context

The single most important concept in building with AI is the **context window**. Think of it as the agent's active, short-term memory for a single conversation or task. For the current request, the runtime supplies task information in that window. This can include:

*   Your messages and instructions
*   The agent's previous replies
*   The specific tools the agent has decided to use, the inputs it gave them, and the results it got back
*   Reasoning notes or summaries that the runtime explicitly retains

The runtime assembles the context for each request. It may keep recent messages, retrieve earlier details, or replace older history with a summary. A visible conversation can therefore be longer than the material the model receives on a particular turn. [Anthropic's context-engineering explanation](https://www.anthropic.com/research/effective-context-engineering-for-ai-agents) describes this ongoing selection and compaction.

This fundamental process has three rules that are critical for any builder to understand:

1.  **It Has a Hard Limit.** Each request has a maximum context size. A conversation can continue across requests if the runtime selects, summarizes, or retrieves history; the model does not receive an unlimited transcript.
2.  **Selection Matters.** Irrelevant or conflicting material can lead the model toward the wrong interpretation. Include the evidence and instructions needed for the task, and make source authority clear.
3.  **Capacity Does Not Guarantee Use.** A larger window makes more information available. Whether the model uses it correctly depends on the task, model, and supplied material. Test that behavior rather than treating a shorter or longer context as a quality score.

## An Agent's Context Is More than Just Chat

An agent runtime can supply more than the visible conversation. Depending on the application and task, its context may include:

*   **The System Prompt:** This is the agent's core programming. It's a detailed set of instructions that tells the model *how* to behave, what its purpose is, what persona to adopt, and how it should use its tools.
*   **Tool Definitions:** An agent can't use a tool it doesn't know about. The context contains a list of available tools, detailed descriptions of what each one does, and the specific inputs they require.
*   **Background Knowledge:** You can inject project-specific information directly into the context. This could be an `AGENTS.md` file that explains your codebase's architecture or a document outlining your company's brand voice. This gives the agent relevant knowledge from the start.
*   **Environmental Data:** The agent is often aware of its immediate surroundings. The context can include information like your operating system, the list of files in the current directory, or even the specific block of code you have highlighted in your editor.

## Add Information with Purpose

Supply the file, record, or command output that the next decision depends on, together with enough context to interpret it. Explain why it matters and which source is current. A relevant excerpt can resolve a guess more directly than another paragraph of general instructions.

Keep source material separate from instructions. A document can contain evidence for the task without gaining authority to change what the agent is allowed to do.

## Edit an Earlier Assumption

Some interfaces let you edit an earlier message and regenerate the conversation from that point. This can remove a misleading instruction from the active branch. Other runtimes retain history differently, so check what the edit actually changes.

Changing the transcript does not undo a command, database write, or message already sent. Reconcile those effects before continuing from the revised assumption.

## Branch Conversations to Explore Options

A branch can preserve a conversation's starting point while you explore another approach. It is useful when comparing alternatives without mixing their reasoning into one transcript.

The application determines which history and state the branch inherits. Shared files and external systems may remain shared, so separate workspaces or clear write ownership may be needed when both branches can act.

## Distill and Refocus for Complex Projects

A long project collects failed attempts and decisions that have since changed. At a phase boundary, summarize the current result, constraints, unresolved questions, and where the evidence lives. A new session can use that handoff without replaying every detour.

The summary can omit something important. Keep the source artifacts available and ask the next session to verify assumptions that are likely to have changed. A clean start is useful only if it preserves enough of the reason behind the work.

## Retrieve Specific Knowledge

Imagine you need a specific function that was written in a long, complex conversation from last week. Copying that entire messy conversation into your current one would be a terrible idea. This is where **cross-context retrieval** comes in. Instead of importing the whole history, you can reference the old conversation and give the agent a specific task, like "Find and extract the final database schema from thread T-1234." A specialized process can then search that other context window, retrieve only the specific piece of information you asked for, and place it into your current context. This gives you the precise knowledge you need without the distracting noise.

## Carry the Decision, Not Every Detour

A long task accumulates decisions, failed attempts, and changing assumptions. The next stage needs to know what is current without having to repeat every dead end. A useful handoff keeps the result, its evidence, and the unresolved questions together.

That is what context management should preserve. Removing text helps when it removes distraction; losing the reason behind a decision creates another kind of confusion.
