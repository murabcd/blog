## The Dashboard Queue

Someone in sales needs an answer about a customer trend. The data is in the warehouse, but finding the right tables and interpreting them still requires an analyst. A ticket enters the queue, and a small business question becomes another reporting task.

A data agent can help with that translation. It can inspect schemas, read transformation code, and draft a query from a question in ordinary language. The hard part is making the answer trustworthy enough that the team can use it without reconstructing the analysis themselves.

## Context beyond the Semantic Layer

A semantic layer records agreed definitions such as revenue, active users, and retained customers. It gives the organization consistency, but it also needs maintenance as the product and data model change.

Agents can supplement those definitions by investigating transformation code and application logic on demand. That helps when a question falls outside the metrics already modeled. The investigation should still respect agreed definitions; an agent that invents its own meaning of revenue makes comparison harder.

I would keep stable business definitions explicit and let the agent explore the details around them. That provides flexibility without asking every query to rediscover what the company means.

## The Scout and the Builder

A useful workflow separates investigation from query generation. A focused first pass identifies tables, column meanings, join relationships, filters, and relevant business rules. It returns a brief the query-writing step can use and inspect.

That brief reduces guessing, but it needs evidence. Include source references and unresolved questions. A column name that looks right may have a different meaning, and two plausible joins can produce different answers.

After writing the query, validate it against the schema and inspect intermediate results where practical. The separation makes errors easier to locate; it does not guarantee correct SQL or correct business reasoning.

## Capturing Tribal Knowledge

An analyst may know that an orders table contains multiple rows for split shipments. If the agent counts rows as orders, the query can execute successfully and still overstate the result.

Record the correction with its scope, source, and date. Retrieve it for related questions and review it when the schema changes. A searchable memory helps only if old advice does not quietly become a permanent rule after the underlying behavior changes.

Useful corrections should become shared knowledge that people can inspect. Keep a distinction between a verified business rule and a suggestion from one conversation.

## The Self-Correction Loop

A second review can compare the query with the original question: time window, segment, aggregation, and join behavior. It can also examine suspicious results, such as an unexpected multiplication of rows.

A model reviewing its own work can repeat the same misunderstanding. Use deterministic checks and known-answer examples where available, and surface material uncertainty rather than silently retrying until an answer looks convincing. Bound the recovery loop so a difficult question does not become an endless sequence of calls.

## Bringing It to the Team

I built an open-source project for my team called [Omni](https://github.com/murabcd/omni) to connect data access with daily workflows. It can work with analytics in PostHog, issues in Jira and Yandex Tracker, and information from tools such as Figma and Google Docs.

The point is to let someone start with the question in chat rather than first deciding which tool to open. The agent can coordinate the available operations and return the evidence alongside the answer. Access and available integrations still determine what it can actually complete.

## Make the Answer Reviewable

Self-serve analytics works when someone can understand what was counted, which definition was used, and where the evidence came from. A fast answer without those details can move the analyst's work downstream to the person trying to trust it.

Start with a narrow set of recurring questions and compare agent answers with reviewed results. Expand access as the system demonstrates that it handles the definitions and failure cases the team depends on.
